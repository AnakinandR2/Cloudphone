## 2. 接进《测试计划》§8 缺陷管理流程的哪一环
| §8 既有环节 | 外部黑盒来源如何接 |
|---|---|
| 发现→记录 | 我方完成（黑盒复现+三端证据）→ 直接产出一条结构完整的 GitLab issue |
| 定级 | 用你们的 S1–S4（同一套·我方已按此标） |
| 修复 | 你们正常修；commit 建议 `fix(模块): … \n\nCloses #<iid>` |
| **回执** | 修完在 issue 评论填下方 `fix-receipt`（驱动我方版本闸复测） |
| 回归→关闭 | 我方用 ≥`fixed_in` 的版本**真复测**通过 → 关单（防"改了但没真好"的假阳） |

## 3. 修复后请回什么（fix-receipt）
close issue 时在评论保留并填写：
```yaml fix-receipt
fixed_in: ""          # 🔴 必填·修复 commit sha（本仓暂无 tag）—— 驱动"复测版本≥fixed_in"闸
verdict: fixed         # fixed | external | not-a-bug
fix_summary: ""        # 修复说明
impact_scope: ""       # 影响面
dev_selftest: ""       # 自测结果
related_mr: ""         # 可选
```
- `verdict=fixed` 我方**不直接判已验证**，会真复测过版本闸才关。
- `verdict=external`（属中台/上游）/ `not-a-bug`（不予修复）→ 我方据此转外部/待确认。
- 只 close + 关联 commit/MR 不填回执也行（我方人工兜底推 `fixed_in`），但填了最省事。
