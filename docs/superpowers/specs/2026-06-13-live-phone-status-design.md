# 云手机状态「展示纯实时」设计

- 日期：2026-06-13
- 问题：业务前台展示的云手机状态经常与中台真实状态对不上。
- 目标：用户可见的状态一律在**读取时实时查中台**，本地不再作为展示来源；查不到则显示「未知/同步中」。

## 1. 背景与根因

当前 `cloud_phones.status` 既是**展示来源**又是**内部状态机**（worker 收敛、欠费执行、计费护栏、操作门禁）。展示侧虽有 `enrichStatuses` 在列表上用中台实时态覆盖，但仍有三处漏洞导致「对不上」：

1. **详情/单台读不富化**：`GetByID` 等返回本地档案值（陈旧）；只有列表富化。
2. **`enrichStatuses` 失败静默回退本地**：中台查询失败/超时时显示可能已过期的本地值，且「伪装准确」。
3. **UI 与后端门禁不同源**：前端按钮 `canPowerOn/Off/Destroy` 用的是（已被覆盖的）实时态，后端 `Power/Delete` 却用本地档案态判门禁 → UI 给了按钮、后端却拒绝。

## 2. 原则（已与用户确认）

- 本地 `status` **不再是用户展示来源**，仅供后台内部（worker 收敛 / 欠费执行 / 计费护栏 / 操作门禁兜底）。
- **所有用户可见的状态读取时实时查中台**；查不到 → `UNKNOWN`（「同步中/未知」），**不回退本地档案值**。
- **纯实时、不缓存、不乐观覆盖**（用户明确选择，取舍见 §7）。

## 3. 核心：服务端实时状态解析（统一入口）

新建 `resolveLiveStatuses(phones []CloudPhone)`：就地把每台的展示状态改为中台实时态。

- 对有 `cpId` 的手机：批量查中台 §2.8 `/cloud-phone/batch-query-status`（状态专用、比 §2.6 page 轻），按中台 18 态映射到展示态。
- **查询失败 / 该 cpId 不在返回结果里 → `UNKNOWN`**（不静默回退本地）。
- 无 `cpId`（未开通实例）→ 保留本地 `CREATED / CREATE_FAILED`（中台无可查）。
- **不加缓存**。

替换现有 `enrichStatuses`（其失败回退本地的行为被 `UNKNOWN` 取代），并**应用到所有用户读**：
- `GetList`、`AdminList`（现已富化，改为新逻辑）。
- `GetByID` / 详情（**当前缺口，本次补上**）。
- 任何把云手机状态回前端的单台读（远控/群控详情等）。

映射函数 `mapMidplatStatus` 对齐中台规范 §2.6 的完整 18 态 → 展示态，并补 `UNKNOWN`。

## 4. `UNKNOWN` 状态

- 后端新增常量 `StatusUnknown = "UNKNOWN"`。
- 前端：新徽章「同步中/未知」（灰色，脉冲）；门禁 `canPowerOn/canPowerOff/canDestroy/isRunning` 对 `UNKNOWN` 一律返回 false（不提供操作，提示稍后刷新）。

## 5. 操作门禁改读实时（消除 UI/后端不一致）

`Power`（开/关机）、`Delete`（销毁）的门禁从「本地档案态」改为「**操作时实时查该 cp**」：

- 操作入口先实时解析该 cp 的展示态，再判允许集合（开机：`STOPPED/CREATED`；关机：`RUNNING`；销毁：`STOPPED/CREATED/CREATE_FAILED`）。
- 实时态为 `UNKNOWN`（中台不可用）→ 拒绝并提示「状态未知，请稍后重试」。
- 中台自身的非法操作校验作为兜底，错误透传给用户。
- 这样「UI 显示什么 → 后端就按什么判」，对不上的根因消除。

> 注：下发操作后仍会写本地态（`STARTING/STOPPING/DESTROYING`）+ 建 `CpTask`，供 worker 收敛与内部门禁；这些是**内部**用途，不影响展示（展示永远实时）。

## 6. 前端

- 列表/详情徽章与操作按钮全部基于后端返回的实时状态；前端不缓存本地态。
- `UNKNOWN` 徽章 + 门禁置灰。
- 轮询：过渡态仍每 4s 静默刷新（现状保留）。因不做乐观覆盖，下发操作后短暂可能仍显旧态，靠按钮 `opBusy` 禁用避免重复点击。

## 7. 已确认取舍（写明）

- **纯实时不缓存**：多用户 × 4s 轮询会放大中台调用量，可能触发 §2.6/§2.8 `RATE_LIMITED`。作为已知取舍记录。可选缓解（不引入缓存、可后续做）：仅页面可见时轮询、调长轮询间隔、列表批量查一次覆盖该用户全部 cp。
- **纯实时不乐观**：下发开/关/销毁后数秒内可能仍显示旧态，由 `opBusy` 兜重复点击。

## 8. 范围 / 不做

- **内部 cron 维持本地态不动**：`worker` 收敛、`runEnforcement`、运行护栏仍按本地 `status` 判（内部、非用户可见），本次不改，避免牵连状态机/收敛/计费正确性。
- 不引入状态缓存、不引入中台 webhook 回调。

## 9. 测试

- `resolveLiveStatuses`：18 态映射齐全；cp 不在返回 / 查询失败 → `UNKNOWN`；无 cpId → 用本地值。
- 详情 `GetByID` 现在返回实时态。
- 操作门禁按实时态放行/拒绝：用 fake 中台喂不同实时态，验证 `Power/Delete` 对 `RUNNING/STOPPED/UNKNOWN` 的允许/拒绝；`UNKNOWN` 拒绝。
- 前端：`UNKNOWN` 徽章渲染、门禁置灰。
- 后端 `go build/vet/test ./...`、前端 `pnpm build` 通过。

## 10. 验收标准

1. 列表、详情、单台读的状态均来自中台实时；中台不可用时显示「同步中/未知」，不显示陈旧本地值。
2. 前端能点的操作，后端按同一实时态判，不再出现「能点但被拒」。
3. 内部 worker/欠费/护栏行为不变。
4. 构建与测试通过。
